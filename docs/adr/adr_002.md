# ADR 02: Banco de Dados por Serviço

- Data: 2026-04-20
- Status: Aceito

## Problema

Escolher banco de dados para cada serviço considerando: prazo curto, sem orçamento, integrações já conhecidas.

## Opções Consideradas

**PostgreSQL** é grátis, open source, muito confiável com JSON nativo. Migrations funcionam bem com Prisma, Knex e Ecto. Todo time conhece, então risco técnico é baixo.

**MySQL** também é grátis e popular com setup rápido, mas suporte a JSON é limitado e menos confiável que Postgres em edge cases.

**MongoDB** oferece schema flexível (ótimo pra MVP) e é grátis. Problema é que o time não conhece bem, não tem transações ACID confiáveis (crítico em orders) e seria risco em 2 semanas.

**Redis** é super rápido e grátis, excelente para cache e sessions. Mas não é persistente (risco de perder dados críticos) e não substitui um BD real.

**SQLite** tem zero configuração e é rápido pra prototipar. Problema é que não escala bem com concorrência e é arriscado pra produção em 2 semanas.

## Decisão

Escolhemos **PostgreSQL para todos os serviços**. Transações são críticas em autenticação, payment e order processing - não podemos perder dados ou deixar estado inconsistente. O time já conhece bem, migrations estão prontas pra cada linguagem (Prisma/Node, migrations em Go, Ecto/Elixir), é totalmente grátis, e temos um strategy único pra backup. Com 2 semanas de prazo e sem orçamento, adicionar outra tecnologia de BD (MongoDB, Redis como persistência) é overhead que não cabe. Se performance ficar ruim, adicionamos Redis pra cache depois, mas começa simples.

## Risco & Mitigação

Postgres pode ficar lento em order-service (muito traffic, muitas transações) - resposta é adicionar Redis pra read-heavy depois se medir problema real. Conexões podem esgotar se não gerenciar pool direito - mas Prisma (Node) e Ecto (Elixir) já fazem connection pooling nativo, então é configuração. Migrations podem quebrar - resposta é testar local antes de deploy, com rollback automatizado pra cada serviço.

**Estratégia: Postgres first, depois otimiza se medir problema.**
