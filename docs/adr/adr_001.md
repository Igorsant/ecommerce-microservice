# ADR 001: Escolha de Linguagens por Serviço

**Status:** Aceito  
**Data:** 2026-04-20  
**Autores:** Time de Arquitetura

---

## Contexto

O sistema é composto por quatro microsserviços com responsabilidades distintas. Em vez de padronizar em uma única linguagem, o time optou por permitir que cada serviço use a linguagem mais adequada ao seu domínio, levando em conta:

- Características técnicas da linguagem em relação à responsabilidade do serviço.
- Conhecimento prévio do time.
- Prazo de entrega de duas semanas sem orçamento para novos toolings.
- Necessidade de que cada serviço seja deployável e maintainable de forma independente.

| Serviço          | Linguagem / Framework         |
|------------------|-------------------------------|
| user-service     | Go                            |
| product-service  | Node.js                       |
| order-service    | Elixir / Phoenix (Ecto)       |
| payment-service  | Node.js (Knex)                |

---

## Opções Consideradas por Serviço

### user-service → Go

**Por que Go:**
- O `user-service` é um serviço de perfil com operações predominantemente de leitura (CRUD simples), onde a baixa latência e o consumo mínimo de memória do Go são vantagens diretas.
- A concorrência nativa (goroutines) permite lidar com múltiplas requisições simultâneas sem overhead de thread por requisição.
- O binário compilado tem startup quase instantâneo — vantagem em ambientes containerizados.
- O time quis exercitar Go num serviço de baixo risco de negócio, onde um bug tem impacto menor que em order ou payment.

**Alternativas descartadas:**
- **Node.js:** teria funcionado, mas o objetivo era ter diversidade deliberada de stacks para validar a independência dos serviços.
- **Rust:** performance superior ao Go, mas curva de aprendizado proibitiva no prazo de duas semanas.

---

### product-service → Node.js

**Por que Node.js:**
- O `product-service` expõe um catálogo de produtos com operações de leitura pesada e mutations simples (criar, atualizar preço, atualizar estoque).
- Node.js com Express é o stack de menor fricção para o time nesse tipo de CRUD — sem necessidade do rigor de TypeScript num domínio sem lógica de negócio complexa.
- Integração direta com PostgreSQL via drivers maduros (pg, knex) sem overhead de ORM.

**Alternativas descartadas:**
- **TypeScript:** considerado, mas o serviço não tem lógica de domínio que justifique o overhead de compilação no ciclo de desenvolvimento curto.
- **Python / FastAPI:** performático e com bom suporte a async, mas adicionaria uma linguagem ao mix sem ganho real nesse contexto.

---

### order-service → Elixir / Phoenix (Ecto)

**Por que Elixir:**
- O `order-service` é o domínio de maior complexidade de negócio: criação de pedidos com múltiplos itens, validação de estoque, snapshot de preço e transições de status (pending → paid → cancelled).
- A imutabilidade de dados e o pattern matching do Elixir tornam explícitas as transições de estado — cada `case` ou `with` representa um caminho do fluxo do pedido, reduzindo estados implícitos.
- O modelo de atores do OTP (GenServer, Supervisor) garante isolamento de falhas: uma falha ao processar um pedido não derruba o processo do serviço inteiro.
- Ecto fornece transações explícitas via `Multi`, essencial para garantir que a criação do pedido e o snapshot de preço sejam atômicos.
- A tolerância a falhas por design se alinha com a criticidade do domínio: pedidos não podem ser perdidos silenciosamente.

**Alternativas descartadas:**
- **Node.js:** funcional para o CRUD, mas o gerenciamento de estado assíncrono complexo (múltiplos itens, validações encadeadas) em JavaScript tende a ficar difícil de rastrear sem o pattern matching e a imutabilidade do Elixir.
- **Java / Spring Boot:** robusto para domínios complexos, mas verboso demais para o prazo e sem nenhum membro do time com experiência recente no stack.
- **Go:** concorrência nativa é uma vantagem, mas a ausência de pattern matching e a verbosidade no tratamento de erros tornam o Go menos expressivo para modelar fluxos de negócio com múltiplos estados.

---

### payment-service → Node.js (Knex)

**Por que Node.js com Knex:**
- O `payment-service` integra com um gateway de pagamento externo e persiste o resultado — fluxo linear com poucos estados (pending → approved | refused).
- Knex foi escolhido sobre um ORM completo (Prisma, Sequelize) para ter controle explícito das queries, importante num contexto financeiro onde queries inesperadas podem causar inconsistência.
- Node.js é adequado para I/O-bound workloads (chamadas ao gateway de pagamento são operações de rede), e o time já domina o stack.

**Alternativas descartadas:**
- **TypeScript:** o serviço tem schema simples e lógica linear; o ganho de tipos não compensava o overhead no prazo.
- **Elixir:** tolerância a falhas seria vantajosa, mas o time já estava usando Elixir em order-service e não havia capacidade de manter dois serviços Elixir com qualidade no prazo.
- **Go:** viável, mas o time priorizou Go apenas no user-service para manter o escopo de aprendizado gerenciável.

---

## Decisão

Cada serviço usa a linguagem mais adequada ao seu domínio e ao conhecimento do time no momento:

- **Go** onde performance e baixa footprint são prioritários num serviço de leitura pesada (user).
- **Node.js** onde a velocidade de desenvolvimento supera outros critérios num domínio simples (product, payment).
- **Elixir** onde a complexidade de domínio e a tolerância a falhas são requisitos não negociáveis (order).

A heterogeneidade de linguagens é um custo aceito conscientemente. Cada serviço é independente o suficiente para que o time possa trabalhar num serviço sem precisar conhecer os internos dos outros.

---

## Consequências

### Positivas
- Cada serviço usa a ferramenta mais adequada à sua responsabilidade, sem compromissos forçados por uma linguagem única.
- A independência de deploy é reforçada: uma mudança de linguagem futura num serviço não afeta os demais.
- O isolamento de domínios é natural — não há tentação de compartilhar código entre serviços porque os stacks são diferentes.

### Negativas / Trade-offs
- O time precisa ter proficiência mínima em Go, Node.js e Elixir simultaneamente — o conhecimento não é totalmente transferível entre serviços.
- Tooling de observabilidade (logs, tracing, métricas) precisa ser configurado separadamente para cada stack.
- Onboarding de novos membros é mais lento: entender o sistema completo exige conhecimento de três linguagens.

### Riscos Identificados
- Concentração de conhecimento: se o único desenvolvedor com experiência em Elixir sair, o `order-service` fica em risco. Recomenda-se documentação interna e pair programming para distribuir o conhecimento.
- Inconsistência de padrões: sem um guia de estilo por linguagem, cada serviço pode evoluir com convenções diferentes, dificultando a leitura cruzada de código.
