# ADR 003: Comunicação entre Microsserviços

**Status:** Aceito  
**Data:** 2026-04-24  
**Autores:** Time de Arquitetura

## Opções Consideradas

### Opção A: REST / HTTP síncrono ✅ Escolhida

Comunicação via HTTP com JSON. Cada serviço expõe endpoints REST; chamadas entre serviços são requisições HTTP diretas.

**Prós:**
- Onboarding imediato: todos os membros do time já dominam REST/HTTP, sem curva de aprendizado.
- Ferramentas de observabilidade padrão (logs HTTP, status codes, curl, Postman) funcionam sem configuração extra.
- Depuração trivial: qualquer desenvolvedor pode reproduzir uma chamada entre serviços com uma simples requisição HTTP.
- Contrato explícito via status codes HTTP (200, 201, 404, 422) e JSON bem definido — sem necessidade de schema registry.
- Compatível com os cinco stacks do projeto (Node.js, Go, Elixir) sem binding de library específica.

**Contras:**
- Acoplamento temporal: o serviço chamador depende da disponibilidade do serviço chamado no momento da requisição.
- Sem garantia de entrega para as chamadas de notificação (ex.: `auth-service → user-service`); falhas exigem retry manual ou outbox pattern.

---

### Opção B: gRPC

Comunicação via HTTP/2 com Protocol Buffers. Contratos definidos em `.proto` files, geração de código cliente/servidor.

**Por que foi descartado:**
- Requer geração de código para cada linguagem (Node.js, Go, Elixir), adicionando um passo de build por serviço.
- O payoff em performance (binary serialization) não justifica o custo operacional num volume de tráfego interno baixo a moderado.
- Debugging mais difícil: não é possível inspecionar o payload diretamente sem ferramentas específicas (grpc-curl, BloomRPC).
- A heterogeneidade de stacks aumenta a superfície de manutenção dos `.proto` files — qualquer mudança de contrato exige regeneração em todos os serviços.

---

### Opção C: Message Broker (RabbitMQ / Kafka)

Comunicação assíncrona via filas ou tópicos. Produtores publicam eventos; consumidores os processam independentemente.

**Por que foi descartado como protocolo principal:**
- Introduz uma peça de infraestrutura crítica (broker) que precisa ser provisionada, monitorada e mantida pelo time.
- Consultas que exigem resposta imediata (ex.: `order-service` buscando preço do `product-service`) não se encaixam naturalmente no modelo assíncrono — exigiriam padrões request/reply sobre filas (correlation ID), que são mais complexos que uma simples chamada HTTP.
- O time não tem experiência operacional com brokers distribuídos; o custo de adoção seria alto relativamente ao tamanho atual do sistema.
- Aceito como evolução futura: para fluxos de notificação de estado (ex.: resultado do pagamento), um broker traria durabilidade e desacoplamento — mas isso pode ser introduzido incrementalmente quando o volume justificar.

---

### Opção D: GraphQL

API de consulta flexível via um schema tipado. Clientes declaram exatamente os campos que precisam.

**Por que foi descartado:**
- GraphQL resolve o problema de over-fetching em APIs públicas voltadas para múltiplos clientes (web, mobile) — não é o problema central aqui, onde os consumidores são serviços internos com contratos conhecidos.
- Adiciona complexidade de schema, resolvers e potencial N+1 queries sem benefício claro para comunicação serviço-a-serviço.
- Nenhum dos serviços atualmente expõe GraphQL; adotá-lo apenas para comunicação interna criaria dois paradigmas sem justificativa.

---

## Decisão

A comunicação entre serviços será feita via **HTTP síncrono (REST)** para operações que exigem resposta imediata (consultas e validações) e via **HTTP síncrono de notificação** para propagação de estado após a conclusão de uma operação.

**Justificativa da escolha:** REST foi escolhido por ser a opção com menor custo de adoção dado o contexto atual — time poliglota sem expertise em brokers, volume de tráfego que não justifica infraestrutura adicional, e necessidade de depuração ágil durante o desenvolvimento. A consistência eventual introduzida pelas chamadas de notificação (ex.: `auth-service → user-service`) é um trade-off aceito, mitigável com retry e outbox pattern quando necessário.
